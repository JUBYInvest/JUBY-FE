**코드를 고치기 전에 먼저 본다.** 고친 항목은 지우고, 새로 찾은 문제는 여기에 적는다.

## 고치지 않은 것

1. **로그인 리다이렉트는 붙었다(모양이 달라 G-1로 맞춤). 실서버 로그인은 여전히 못 해 봤다**(JUBY-BE dev `7e5b023`, 2026-09-28).
   2026-09-30 백엔드(`https://api.juby.store`)와 프론트(`https://juby-fe.vercel.app`, `main`)가 배포됐다. 재발급·온보딩도 지은 응답으로만 쟀다.
   로그인 상태의 수정(성향 404, 저장 실패·다시 저장, 토큰 규칙, 관심종목, 진입 시 401, 로그인 뒤 돌아갈 곳, 로그아웃, 내 정보 수정
   G-2·G-4, AI 새 대화 G-3)은 콜백 주소를 직접 열어 흉내 낸 것뿐이다. 배포에 올라갔는지 확인되면 이 흐름부터 실제로 돌려 본다.
   배포에서는 RT 쿠키·CORS 문제(아래 "백엔드·배포에 넘길 것" 4·5)가 먼저 걸릴 수 있다.
2. 응답의 빈 값 중 화면에 맡긴 자리가 남아 있다(코드에서 `unchecked(`로 찾는다). 전부 포맷 함수가 "-"로 적거나 화면이
   쓰지 않는 값이다 — 2026-09-27에 화면이 받아내지 못하던 자리(목록 행 코드·이름, 성향 문항·저장 응답, 뉴스 전체 개수)는 막았다.
3. **백테스트 수익률 0%(백엔드)**: 기간 끝 보유 포지션 미청산 + 비율 컬럼 소수 둘째 자리 + AI 요약 단위.
   원인과 수정안은 CLAUDE.md "백엔드 사정 > 백테스트". 백엔드가 고치고 운영 DB에 ALTER + 프리셋 배치를 다시 돌리면
   프론트는 고칠 것 없이 맞게 보인다. 그 전까지 거래 0회로 끝까지 들고 있던 결과는 화면이 임시 안내로 알린다
   (`isHeldToEnd`) — **백엔드가 고치면 그 안내를 지운다.** 끝난 거래 뒤에 다시 사서 들고 있는 결과는 프론트가 가려내지
   못해 수익률이 덜 잡힌 채로 안내 없이 보인다. 비율이 소수 둘째 자리로 잘려 "23.00%"처럼 정밀해 보이는 것도 그대로다.
4. 비로그인 성향테스트는 문항 GET이 401이라 늘 임시 7문항 + "서버 문항을 불러오지 못해" 안내가 뜨고, 백테스트 기간 옵션 401 때
   "서버 목록을 받지 못해…" 안내가 뜬다(G-5는 실행 결과의 401만 로그인 안내로 바꿨다). 아래 "결정 대기"의 비로그인 항목에 달렸다.

## 백엔드·배포에 넘길 것 (수정 지시서 2026-09-28 4절, 그대로 옮김)

프론트는 하지 않는다. 전부 JUBY-BE `dev` `7e5b023` 소스 기준이다(2026-09-28 GitHub에서 읽기만 해 확인).

1. **공개 범위.** permitAll에서 `/api/backtest/**`·`/api/personality-tests`가 빠졌다(`d7edec4`, 커밋 메시지에 언급 없음). 의도인지 묻는다. 공개로 두려면 되돌린다.
2. **생년월일 지우기.** `Member.updateInfo`가 null을 "안 바꿈"으로 본다. 지우기를 지원할지 정한다. 지원하면 "안 보냄"과 "지움"을 가를 표시가 필요하고, 프론트는 G-2 막음을 걷는다.
3. **이름 검사.** `ChangeMemberInfo`의 `@Size`가 `javax.validation.constraints.Size`라 Boot 3(jakarta)에서 검사되지 않는다. jakarta로 바꾸면 살아난다. 프론트는 G-4로 바뀐 이름만 보내므로 긴 기존 이름도 문제없다.
4. **CORS.** 허용 출처가 `FRONTEND_URL` 하나다. vite 프록시(`changeOrigin: true`)는 Host를 백엔드로 바꾸고, 브라우저는 POST·PATCH·DELETE에 `Origin: http://localhost:5173`을 싣는다. 그래서 `FRONTEND_URL`이 배포 주소면 로컬 개발의 쓰기 요청이 403("Invalid CORS request")이다. 머지 전에는 CORS 설정 자체가 없어서 안 터졌다. `app.cors.allowed-origins`를 `FRONTEND_URL`과 떼어 로컬·배포 주소를 함께 받게 한다. 배포(Vercel 중계)가 같은 문제를 겪는지는 Vercel이 Host를 어떻게 넘기느냐에 달려 있어, 배포에서 확인한다.
5. **RT 쿠키가 배포에서 실리지 않는다.** 쿠키는 소셜 콜백(`BACKEND_URL/login/oauth2/code/*`) 응답이 백엔드 주소에 박는다. 그런데 프론트는 `/api/auth/reissue`를 Vercel 중계(프론트 주소)로 부른다. 브라우저는 다른 호스트의 쿠키를 싣지 않는다. `application-dev.yaml` 주석의 가정(프론트가 백엔드를 다른 사이트로 직접 부르고 `SameSite=None`)은, https 페이지에서 http 백엔드를 직접 부르는 게 mixed content로 막혀 쓸 수 없다. 같은 출처로 맞추려면 `BACKEND_URL`(소셜 redirect-uri)을 프론트 주소로 두고, Vercel·vite 프록시가 `/oauth2/**`·`/login/oauth2/**`도 백엔드로 넘기고, 소셜 개발자 콘솔의 redirect URI를 바꾼다.
6. **배포 확인.** PR #91 머지로 dev 배포 워크플로가 돌았을 것이다. 서버에 올라갔는지, `FRONTEND_URL`·`COOKIE_*` 값이 무엇인지 확인한다.

2026-09-30 덧붙임(위 여섯 항목은 그대로 둔다): 백엔드가 `https://api.juby.store`에 배포됐다. 프론트의 개발 프록시·배포 중계·소셜 로그인 이동을 이 주소로 바꿨다.
- 6번: 서버는 떠 있다(`GET /v3/api-docs` 200). 허용 출처는 `http://localhost:5173` 하나였다. RT 쿠키는 `ea18fec`에서 `Secure; SameSite=None`으로 고정됐다(`COOKIE_*` 변수는 없어졌다).
  배포 주소가 정해지면 허용 출처에 넣어야 배포의 POST·PATCH·DELETE가 막히지 않는다(4번).
- 5번: 백엔드가 https가 돼 "직접 부르면 mixed content로 막힌다"는 전제는 사라졌다. 프론트가 백엔드를 직접 부르고(`VITE_API_BASE_URL`)
  쿠키를 실어 보내는 길도 열렸다 — 대신 허용 출처·`SameSite`·자격 증명 허용이 맞아야 한다. 재발급만 이렇게 붙였다(`ea18fec`의 RT 쿠키가
  `Secure; SameSite=None`). 사파리는 다른 사이트 쿠키를 막아(WebKit으로 확인) 프론트가 `juby.store` 아래로 가야 재발급이 된다.
  파이어폭스는 Playwright 판에서는 실렸지만 실제 브라우저의 쿠키 격리 설정에 따라 다를 수 있어 실기기에서 본다.
- 6번 이어서: 프론트가 `https://juby-fe.vercel.app`에 배포됐다. 허용 출처에 없다(403). `FRONTEND_URL`을 이 주소로 바꿔 달라고 한다 —
  `ea18fec`는 `http://localhost:5173`을 따로 늘 받아서 로컬 개발은 그대로 된다. 소셜 로그인 뒤 돌아오는 곳도 이 값이다.
- 7(새로 찾음, `ea18fec` 소스). **관리용 API가 로그인만 하면 누구나 부를 수 있다.** `@PreAuthorize("hasRole('MANAGER')")`는 `/api/token/*`에만 있다.
  `POST /api/initiate`(일봉 적재), `POST /api/vectordb/all`(전 종목 네이버 뉴스 → Pinecone 일괄 적재), `GET /api/vectordb`,
  `/api/market/**`(증권사 직통 — 호출 제한에 걸린다)는 아무 회원이나 부른다. 같은 역할 검사를 달거나 운영에서 막는다. 프론트는 부르지 않는다.
  시험용 정적 화면(`/mypage.html`·`/openai-test.html`·`/backtest-test.html`)도 운영에서 공개다.
- 8(새로 부탁). `PATCH /api/members/me/personality`가 DB 자동 번호(`personalityId`)만 받아 프론트가 붙일 수 없다. 성향 이름(`안정형` 등)으로
  받거나 번호가 든 성향 목록을 달라고 한다.
