## 백엔드·배포에 넘길 것 (수정 지시서 2026-09-28 4절, 그대로 옮김)

프론트는 하지 않는다. 전부 JUBY-BE `dev` `7e5b023` 소스 기준이다(2026-09-28 GitHub에서 읽기만 해 확인).

1. **공개 범위.** permitAll에서 `/api/backtest/**`·`/api/personality-tests`가 빠졌다(`d7edec4`, 커밋 메시지에 언급 없음). 의도인지 묻는다. 공개로 두려면 되돌린다.
2. **생년월일 지우기.** `Member.updateInfo`가 null을 "안 바꿈"으로 본다. 지우기를 지원할지 정한다. 지원하면 "안 보냄"과 "지움"을 가를 표시가 필요하고, 프론트는 G-2 막음을 걷는다.
3. **이름 검사.** `ChangeMemberInfo`의 `@Size`가 `javax.validation.constraints.Size`라 Boot 3(jakarta)에서 검사되지 않는다. jakarta로 바꾸면 살아난다. 프론트는 G-4로 바뀐 이름만 보내므로 긴 기존 이름도 문제없다.
4. **CORS.** 허용 출처가 `FRONTEND_URL` 하나다. vite 프록시(`changeOrigin: true`)는 Host를 백엔드로 바꾸고, 브라우저는 POST·PATCH·DELETE에 `Origin: http://localhost:5173`을 싣는다. 그래서 `FRONTEND_URL`이 배포 주소면 로컬 개발의 쓰기 요청이 403("Invalid CORS request")이다. 머지 전에는 CORS 설정 자체가 없어서 안 터졌다. `app.cors.allowed-origins`를 `FRONTEND_URL`과 떼어 로컬·배포 주소를 함께 받게 한다. 배포(Vercel 중계)가 같은 문제를 겪는지는 Vercel이 Host를 어떻게 넘기느냐에 달려 있어, 배포에서 확인한다.
5. **RT 쿠키가 배포에서 실리지 않는다.** 쿠키는 소셜 콜백(`BACKEND_URL/login/oauth2/code/*`) 응답이 백엔드 주소에 박는다. 그런데 프론트는 `/api/auth/reissue`를 Vercel 중계(프론트 주소)로 부른다. 브라우저는 다른 호스트의 쿠키를 싣지 않는다. `application-dev.yaml` 주석의 가정(프론트가 백엔드를 다른 사이트로 직접 부르고 `SameSite=None`)은, https 페이지에서 http 백엔드를 직접 부르는 게 mixed content로 막혀 쓸 수 없다. 같은 출처로 맞추려면 `BACKEND_URL`(소셜 redirect-uri)을 프론트 주소로 두고, Vercel·vite 프록시가 `/oauth2/**`·`/login/oauth2/**`도 백엔드로 넘기고, 소셜 개발자 콘솔의 redirect URI를 바꾼다.
6. **배포 확인.** PR #91 머지로 dev 배포 워크플로가 돌았을 것이다. 서버에 올라갔는지, `FRONTEND_URL`·`COOKIE_*` 값이 무엇인지 확인한다.

2026-09-30 덧붙임(위 여섯 항목은 그대로 둔다): 백엔드가 `https://api.juby.store`에 배포됐다. 프론트의 개발 프록시·배포 중계·소셜 로그인 이동을 이 주소로 바꿨다.

  배포 주소가 정해지면 허용 출처에 넣어야 배포의 POST·PATCH·DELETE가 막히지 않는다(4번).

  일봉까지 함께 500이라 상세 차트가 안 뜬다(현재가만 비워 주면 프론트는 "-"로 그린다).
  더 읽어 보니(같은 소스) 토큰이 DB에 살아 있으면 발급 없이 쓰므로 한도가 없다. 평일 16시 `DailyPriceScheduler`가
  휴장일 조회(`getHolidayList`, 실전 토큰)로 토큰을 받아 쓰기 트랜잭션에서 저장하고, 24시간 뒤(`isValid`는 10분 앞당김)
  끝난다. 그래서 **토 16시 무렵부터 월 16시까지** 상세가 1분에 1건만 된다(2026-10-04은 일요일이었다). 평일에 실서버로 재 보지는 않았다.
  고칠 곳: `TokenService` 저장을 `REQUIRES_NEW`로 떼거나 상세를 읽기 전용 밖에서 부르기, 그리고 현재가 실패를 잡아
  `dailyPrices`는 내려 주기. 상세는 현재가(증권사)를 DB 일봉보다 먼저 부르고 실패를 잡지 않아 일봉 조회까지 가지 못한다.
  프론트는 홈 카드를 대장주 API로 바꿔 홈에서 이 API를 부르지 않는다. 상세 화면은 여전히 이 API를 쓴다 —
  종목 하나를 본 뒤 곧바로 다른 종목을 누르면 차트가 안 떴다. 그래서 상세는 실패하면 1.5초 뒤 한 번, 그래도 안 되면
  65초 뒤 한 번 더 저절로 부르고, 65초를 기다리는 동안 남은 시간을 적는다. 홈 카드 그래프는 서버에 토큰이 있을 때만 묻는다
  (주말 비로그인 첫 방문이면 "지금은 그래프를 불러올 수 없어요"). 또 로그인한 사용자는 상세 전에 `GET /api/market/{code}/price`를 한 번 불러
  토큰을 저장시킨다 — `/api/market`은 읽기 전용이 아니라 저장되고, 그 뒤 24시간은 모두의 상세가 바로 된다(임시, 사용자 결정,
  CLAUDE.md "증권사(KIS) 호출은 상세 화면과 홈 카드 그래프뿐이다"). 실서버로 확인하지는 않았다(규칙). **고쳐지면 두 장치를 걷는다.**
